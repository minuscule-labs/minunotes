The harness API is the core MinuNotes surface for agents, scripts, OpenAPI tools, and MCP adapters. API keys can access authorized owned folders and explicitly enabled authenticated collaboration grants.

## Auth

Send the API key with every request:

```http
X-API-Key: ntak_...
Content-Type: application/json
```

## Folder access

API keys can use one of three folder access modes:

- **All non-private folders**: access every non-private folder, including future non-private folders.
- **Project roots**: access selected top-level folders and their non-private subfolders.
- **Specific folders**: access only folders explicitly listed on the key.

Global capabilities are a maximum ceiling; folder rules can restrict but never expand it. All access inherits the ceiling where no rule applies; restricted modes require a matching rule, with the nearest exact/subtree rule winning. Folder-level read-only normally blocks writes. Specific access with an applicable exact owned-folder rule is an existing write exception only after the other capability and policy checks pass. Private folders are excluded from API, MCP, and integration access. A private parent also makes its child folders private for API access.

### Shared access

Shared content uses a separate `none | specific | all` mode and defaults to `none`. Specific mode selects active human collaboration grants; all mode includes current and future grants after an explicit warning. Effective access is the intersection of the current human role, credential capabilities, selected shared mode, owner safety policy, and note API-editability.

Full note reads include privacy-safe role/source context. Discovery remains compact, and direct-note grants return null folder context. Shared-folder creation stores new content in the resource owner's corpus and attributes it to the authorizing user. Agents cannot move shared resources, reshare, administer public links, restore, permanently delete, or generally manage Trash. Edit-capable agents may move only eligible creator-owned content to the owner’s Trash. Revocation and downgrade apply immediately.

Folder creation is separate. Only keys with folder-creation permission can call:

```txt
POST /v1/harness/folders
```

Agents can move notes when the key can edit every source folder and create in the target folder. Cross-root moves work only when both sides are inside the key's granted scope.

```bash
curl -s -H "X-API-Key: ntak_..." -H "Content-Type: application/json" \
  -X POST "$API/v1/harness/notes/move" \
  -d '{"noteIds":["note_xxx","note_yyy"],"targetFolderId":"folder_xxx"}'
```

Move responses return compact note metadata and no content.

## Discovery pagination

Folder, tag, note-search, orphan, and cross-note line-search endpoints return compact arrays plus:

```json
{ "pageInfo": { "hasMore": true, "nextCursor": "opaque-cursor" } }
```

Discovery `limit` is 1–100, default 25. Pass `nextCursor` back as `cursor` to the same endpoint with the same query and filters. URL-encode query values and opaque cursors; cross-note line-search cursors do not apply to single-note search. Cursors are scoped to the search and authorized folders, so changing either returns `400`. Continue only when the current page is insufficient; do not fetch every page or expand every note by default.

For a net-new note that does not depend on existing content, resolve the target from folder titles and parent relationships, then create directly. Do not search or read neighboring notes merely to confirm the folder or inspect permissions.

## Owned template management

```txt
GET /v1/harness/folders/:folderId/template-library?limit=25&cursor=...
GET /v1/harness/templates/:templateId
POST /v1/harness/templates
PATCH /v1/harness/templates/:templateId
GET /v1/harness/templates/:templateId/settings
PUT /v1/harness/templates/:templateId/folders/:folderId
PUT /v1/harness/templates/:templateId/defaults
PUT /v1/harness/templates/:templateId/folders/:folderId/defaults
```

Updated Pi (`minunotes_`) and hosted/stdio MCP (`notes_`) expose these tool suffixes: `list_template_library`, `read_template`, `create_template`, `update_template`, `read_template_settings`, `set_template_assignment`, `set_template_tags`, `set_template_property_defaults`. Library discovery is compact, exact-folder and cursor-paginated (25 default/100 maximum); it is separate from destination-assigned templates.

- Creation needs owned source read/create; Markdown only, title 1–1,000 characters and body up to 200,000 characters within the 256-KiB request bound. It does not assign the template or set defaults. No creation receipt: resolve an unknown outcome through library discovery before explicitly creating again.
- Before editing/renaming, read the template; send exact original `expectedTitle`, `contentHash` as `baseHash`, and new `title` and/or `markdown`. Source read/edit and API-editability apply. IDs, assignments, defaults and existing instances stay intact. Preserve drafts and explicitly review conflicts; no automatic retries/rebasing.
- Read settings before changing assignments/tags/defaults. Assign one destination with `assigned` plus settings `membershipSnapshot` as `snapshot`; source and destination owner read/edit are required. Settings include only readable active assignments, never a complete replace-all list. Unassign removes that destination's defaults; unrelated/hidden/trashed assignments stay retained.
- Default tags use the settings tag `revision` as `expectedRevision`. Destination property defaults use that assignment's `id`/`revision` as `assignmentId`/`expectedRevision` plus the current destination folder schema's independent `schemaId`/`schemaRevision`. Submit **complete final** tags/values, preserving unrequested defaults; empty clears only when requested. Stable field/option IDs only, not labels, invented definitions or body hashes. Default tags are not tags on the template note itself.

Shared editor/note grants do not authorize owner administration. Current private/read-only/Trash policies and credential ceilings still apply; no grants, variables or schema inheritance are added. Assigned preview → reviewed ordinary-note creation remains a separate capability with its existing frozen snapshot/request-ID/date-time protocol. Installed/source support does not prove registration or deployment.

## Owned folder structure and reviewed copying

```txt
POST /v1/harness/folders/:folderId/rename
POST /v1/harness/folders/:folderId/move
GET /v1/harness/folders/:folderId/duplicate-preview?parentFolderId=...
POST /v1/harness/folders/:folderId/duplicate
```

Updated Pi/MCP adapters expose `minunotes_rename_folder` / `notes_rename_folder`, `minunotes_move_folder` / `notes_move_folder`, `minunotes_preview_folder_duplication` / `notes_preview_folder_duplication`, and `minunotes_duplicate_folder` / `notes_duplicate_folder`. These are owner-only; shared editor grants do not authorize structural administration.

If a structure result has `parentContext: "unavailable"` and null `parentFolderId`, the parent is hidden—not necessarily Root. A move has no copy receipt: uncertain move outcomes need fresh location review and explicit approval, never replay of a stale move payload. Copy replay rechecks current source/imported-resource availability and limits as well as result access.

Rename uses exact `expectedTitle`; move uses explicit `parentFolderId` (null for Root), exact `expectedParentFolderId` and `confirm: true`. Get approval for the exact subtree/destination: destination-inherited sharing applies. Moves preserve IDs but require whole-subtree edit/read scope, applicable note/template API-editability and retained inherited protection. Cycles, excess depth and leaving scope are rejected; no automatic grant changes.

For copying, preview the exact source/destination first, review token/counts/imageBytes and get explicit approval before confirming with `confirm: true`, literal `title`, `parentFolderId`, `previewToken` and frozen `requestId`. New IDs must inherit existing read/create scope; restricted Root and exact-only destinations are unsupported rather than granted automatically. Source/imported templates/images require read scope, while destination requires read/create and folder-creation permission. Copies preserve native properties/options/boards/templates/defaults/images/links and protection flags, not sharing grants/tokens/history/comments/personal view state. Source API-editability need not permit editing to copy it; copied flags remain unchanged.

On an uncertain result retain the SAME requestId and exact payload; never retry automatically, replace the ID, refresh preview or change the clock. A definitive stale review needs explicit re-review. Execution and receipt replay recheck current authorization; unavailable committed copies are never recreated. MCP copy errors retain status and uncertainty explicitly. New source/tool support does not establish deployment or active session registration.

## Exact-folder notes and note names

```txt
GET /v1/harness/folders/:folderId/notes?limit=25&cursor=...
POST /v1/harness/notes/:noteId/rename
```

Listing returns compact ordinary-note metadata (Markdown/canvas/mind-map), not templates, descendants or content. SQL title/ID keyset pages use the normal 25 default and 100 maximum. Cursors bind the actor, credential and exact folder. A direct-note grant cannot enumerate its containing folder.

Rename accepts only the following fields:

```json
{ "title": "New name", "expectedTitle": "Exact existing name" }
```

Obtain exact `expectedTitle` from current metadata/read; do not normalize it. The new title is trimmed, nonempty and at most 1,000 characters. Body hashes cannot detect another rename and are not used for this title-only operation. Current read/edit scope and API-editability are rechecked transactionally, with compare-and-set and native history/event/link updates. Only ordinary Markdown notes are supported. Body, properties, ID and links remain unchanged. The result is compact metadata plus unchanged contentHash; shared responses always hide containing-folder context. Preserve intent and review on conflicts/uncertain outcomes; do not automatically retry. Body-edit contracts are unchanged.

## Property metadata

Prefer defined folder properties for structured Status/Type labels; use stable property/option IDs, not display labels. Ask if definitions are missing instead of inventing fields/options or mirroring them into tags. Explicit tag requests and reviewed template tags remain supported.

```txt
GET /v1/harness/folders/:folderId/properties
PATCH /v1/harness/folders/:folderId/properties
GET /v1/harness/notes/:noteId/properties
PATCH /v1/harness/notes/:noteId/properties
```

Folder mutation is owner-only: `expectedRevision` plus controlled `mutation` types `add`, `rename`, `reorder`, `archive`, `add_option`, `rename_option`, `archive_option`, `reorder_options`. IDs are server-generated, types immutable; reorder includes all historical IDs. Archive retains values—it is not destructive Delete option.

Read note properties before patching. Copy `schema.schemaId` into `schemaId`, `schema.revision` into `schemaRevision`, and the independent note-properties `revision` into `expectedRevision`:

```json
{
  "schemaId": "schema_from_read",
  "schemaRevision": 1,
  "expectedRevision": 0,
  "values": { "text_property_id": "Reviewed value", "select_property_id": "option_id" }
}
```

Values are optional Text (up to 1,000 characters), Select (one active option ID), or real YYYY-MM-DD Date. Patch only intended active IDs; null clears and empty Text clears. Untouched retained values are preserved. Metadata does not use `contentHash`/`baseHash` and does not change body bytes/hash/tags/versions. Preserve drafts on `409` and review current definitions/values before retrying; stop on `403`/`404` without probing another surface. Direct-note grants allow applicable note metadata, never hidden folder-schema enumeration. Public note reads omit property metadata; shared Boards can show owner-selected Card properties.

## Reviewed template creation

```txt
GET /v1/harness/folders/:folderId/templates
GET /v1/harness/folders/:folderId/templates/:templateId/preview
POST /v1/harness/notes/from-template
```

List destination assignments, preview the chosen assignment, then review the returned Markdown body, default tags/values, destination schema and opaque snapshot. Submit the reviewed destination/template IDs, `snapshot`, `schemaId`, `schemaRevision`, final title, **complete final** tags/values, a caller-chosen `requestId`, and frozen literal `variables`:

```json
{
  "folderId": "reviewed_destination_id",
  "templateId": "assigned_template_id",
  "snapshot": "snapshot_from_preview",
  "schemaId": null,
  "schemaRevision": 0,
  "title": "Reviewed instance",
  "tags": [],
  "values": {},
  "requestId": "one_unique_frozen_request_id",
  "variables": { "date": "reviewed date", "time": "reviewed time", "datetime": "reviewed datetime" }
}
```

Null/0 and empty tags/values above apply only when the reviewed schema/defaults are absent or deliberately cleared. Empty final arrays/maps explicitly clear defaults: retain reviewed tags/values unless the user requests otherwise. Only the original title/date/time/datetime substitutions apply; never send a replacement body. Title is 1–1,000 characters, tags at most 50 with 80 raw characters each, request ID 1–128, variable literals at most 80; request body limit is 256 KiB.

Destination read/create scope and the credential ceiling apply. Editor folder grants may create; direct-note grants may not. Previews do not grant private-library access, and an effectively private source is forbidden. Source API-editability need not permit edits because creation does not edit it. Owner management uses the separate scoped template endpoints.

The result is an ordinary destination-owned note with authenticated provenance: 201 for new, 200 for receipt replay. Body, tags, properties, references, initial version, one create event and receipt commit atomically. On transport/busy/unknown outcome, retain the **same request ID and exact frozen payload** for an explicitly authorized retry; do not refresh the preview, change the clock or use a new ID before resolution. Changed intent with the same key conflicts. A definitive uncommitted stale-review conflict preserves the draft for explicit re-review and a new ID. Completed receipts check current access; inaccessible, moved, trashed or deleted notes are unavailable, never recreated. Snapshots are not access grants. No automatic write retries.

## Web-only agent boundaries

Boards group only by the owner's selected Select property; property writes can regroup cards on refresh. Boards show up to 12 stacked values-only Card properties (Select pills, plain Text/Date), not a special Type badge. Tags never determine placement or synchronize with properties. Retired tag configurations require explicit owner recovery; reads never migrate settings.

Owners configure [Board column visibility](/resources/folders-and-notes) in the web UI. A successful property edit can place a card in a hidden column without changing note access.

Board configuration, personal folder filtering/sorting and destructive option deletion have no Harness/MCP/Pi operations. Existing non-destructive archive, comments, tags and authorized Trash operations remain independent. Source support, installed adapters, registered tools and deployed availability are distinct; do not assume deployment or switch surfaces after denial.

## Trash boundary

The harness API exposes active content only. Trashed notes, templates, and folder subtrees are omitted from folder lists, search, line search, tags, graph results, and attachment access. Direct requests for trashed IDs return not found.

Harness and API-key clients cannot list Trash, restore, or permanently delete content. Focused note/folder Trash operations require explicit destructive intent, human Editor authority, credential edit capability, applicable shared scope, creator ownership, and owner policy. Direct-note grants, shared roots, mixed-creator subtrees, and owner-managed sharing configuration are denied. Owners use the authenticated MinuNotes web interface for restore and permanent deletion. A not-found response can also mean the item is outside the key's scope, so it does not prove permanent deletion.

## Safe editing flow

1. Search or list folders.
2. Read the note because its content is needed for the edit.
3. Capture `contentHash`.
4. Send the smallest relevant edit with `baseHash`.
5. Read back the note and report final Markdown or a changed-section summary.

Create and update responses return compact note metadata plus `contentHash`; they do not include full note `content`. Use the read-note endpoint only when content is needed.

## Review comments

Anchored Review threads are available on active Markdown notes. Comment messages are plain text (Markdown syntax is not rendered), remain external metadata, and never change canonical Markdown.

List threads:

```bash
curl -s -H "X-API-Key: ntak_..." \
  "$API/v1/harness/notes/note_xxx/comments"
```

Create a thread with zero-based offsets, the exact Markdown quote, and the current `contentHash`:

```bash
curl -s -H "X-API-Key: ntak_..." -H "Content-Type: application/json" \
  -X POST "$API/v1/harness/notes/note_xxx/comments" \
  -d '{"body":"Please clarify this.","anchor":{"anchorType":"range","from":42,"to":61,"quote":"exact source text","documentHash":"hash_from_read"}}'
```

Toggle a reaction on one message by posting `{"emoji":"🎉"}` to `/v1/harness/notes/{noteId}/comments/{threadId}/messages/{messageId}/reactions`. Posting the same reaction again removes it. Message responses group reaction counts and identify whether the current actor reacted. The API accepts one standard Unicode emoji, including joined and skin-tone emoji; `👍`, `❤️`, `😂`, `🎉`, `👀`, and `🚀` are quick defaults in the human UI.

Every comment operation requires explicit **Comment** permission plus folder read access. Review-only integrations do not need note edit permission, and `isApiEditable` applies to canonical note edits rather than comments. Existing and new credentials have Comment disabled until the owner grants it. Message edits/deletes are author-only. Stale anchors return `409`; ambiguous anchors are returned as detached rather than moved speculatively. Canvas notes, templates, Trash, and public shares do not expose comments.

## Canvas notes

Canvas notes use `documentType: "canvas.default"` or `"canvas.mindmap"`. Their `content` is serialized JSON Canvas, not markdown. Markdown patch edits are rejected for canvas notes.

Create from JSON Canvas:

```bash
curl -s -H "X-API-Key: ntak_..." -H "Content-Type: application/json" \
  -X POST "$API/v1/harness/canvases" \
  -d '{"folderId":"folder_xxx","title":"Flow","canvas":{"nodes":[],"edges":[]}}'
```

Create from Minu diagram syntax (the endpoint also auto-detects supported Mermaid flowcharts):

```bash
curl -s -H "X-API-Key: ntak_..." -H "Content-Type: application/json" \
  -X POST "$API/v1/harness/canvases/from-syntax" \
  -d '{"folderId":"folder_xxx","syntax":"diagram \"Product plan\" {\n  layout mindmap\n  Product\n  Product > Research\n}"}'
```

Create an editable native canvas from the supported Mermaid flowchart subset. `format` defaults to `auto`; set it to `minu` or `mermaid` to force a parser. Mermaid source is compiled, not retained or rendered as SVG, and unsupported features return diagnostics without creating a partial canvas.

```bash
curl -s -H "X-API-Key: ntak_..." -H "Content-Type: application/json" \
  -X POST "$API/v1/harness/canvases/from-syntax" \
  -d '{"folderId":"folder_xxx","title":"Release flow","format":"auto","syntax":"flowchart LR\n  draft[Draft] --> review{Approved?}\n  review -->|yes| shipped([Shipped])"}'
```

Supported input is Mermaid `flowchart`/`graph` with omitted direction or `TB`/`TD`/`BT`/`LR`/`RL`; explicit or implicit nodes with plain-text labels; rectangle, rounded rectangle, stadium, diamond, circle, and hexagon shapes; directed, undirected, bidirectional, or dotted edges with labels; and nested subgraphs. Styling, classes, click actions, HTML/Markdown labels, icons/images, advanced metadata, and non-flowchart diagram types are rejected. Harness imports enforce 100,000 source characters, 500 native nodes (including groups), 1,000 edges, and 16 subgraph levels.

Replace an existing canvas:

```bash
curl -s -H "X-API-Key: ntak_..." -H "Content-Type: application/json" \
  -X PUT "$API/v1/harness/notes/note_xxx/canvas/from-syntax" \
  -d '{"baseHash":"hash_from_read","syntax":"diagram \"Auth flow\" {\n  User > Login\n  Login > Dashboard\n}"}'
```

Use Minu syntax for mind maps and Mermaid for its supported flowchart subset. Auto-detection recognizes Mermaid `flowchart`/`graph` headers; unsupported Mermaid syntax fails closed. Use raw JSON Canvas for exact imports or deterministic replacements.

### Link canvas nodes to notes

Canvas and mind-map nodes can reference MinuNotes notes through host metadata:

```json
{
  "id": "node_a",
  "type": "text",
  "text": "Project plan",
  "minunotes": {
    "link": { "type": "note", "id": "note_target" }
  }
}
```

Use focused endpoints to add or remove an internal note link without replacing the full canvas:

```bash
curl -s -H "X-API-Key: ntak_..." -H "Content-Type: application/json" \
  -X POST "$API/v1/harness/notes/note_canvas/canvas/nodes/node_a/link-note" \
  -d '{"targetNoteId":"note_target","baseHash":"hash_from_read"}'

curl -s -H "X-API-Key: ntak_..." \
  -X DELETE "$API/v1/harness/notes/note_canvas/canvas/nodes/node_a/link?baseHash=hash_from_read"
```

Linking requires edit access to the canvas and read access to the target note. Internal links contribute to backlinks and graph results with `linkType: "canvas-note"`.

External web links remain in the standard JSON Canvas `node.url` field. Internal link/unlink operations preserve `node.url` and unrelated node metadata, so a node can contain both an external URL and an internal note link.

## Edit payloads

```ts
type DocumentEdit =
  | { type: "append"; text: string }
  | { type: "replace_text"; oldText: string; newText: string }
  | { type: "replace_range"; from: number; to: number; text: string };
```

Prefer `replace_text` when the target text is unique. Use `replace_range` only after reading lines or sections.
